## 1. 术语、源流与长期目标

**已确认：讨论什么层级，就使用该层级的准确名称。**

| 层级 | 术语与边界 |
| --- | --- |
| 框架智能形态 | 辅助智能、模拟智能；认知探索为长期配置方向，不是已冻结的智能等级枚举 |
| 控制角色 | 上位机、下位机；不由认知模块数量自动决定权限 |
| 能力交付与运行单元 | App；不等于所有驱动、智脑模块或用户请求 |
| 产品 | 智能伴侣/伴侣，仅在该产品场景使用；模拟智能不等于伴侣 |

Galatea 是最初项目，Tessera 为具身和工程能力服务；Kaleido 是参考
ESP-Claw 的小项目，逐渐接近 Galatea 雏形，后来以 Tessera 为主合并，
结构过于复杂。用户要求统一身份，取消三者作为新架构并列项目的名称。
Entelea/Forge 是否保留、最终命名和兼容迁移策略待定；不授权删除
原研究仓库、来源、许可或破坏现有 ABI。

延续 Galatea 核心理念：认知机制须有实际因果作用，不把提示词、
自述、变量名、数据库或成功日志冒充感觉、记忆与情感。
现阶段通过 MCU 与 ARM/Linux 逐步探索类脑模块，为未来完整脑奠基；
不承诺近期实现智慧生命全部能力或证明现象意识。
ARM64/x86 不自动等于完整脑，远程复杂推理也不算 MCU 已有完整认知。
认知与 LLM 智能体不是互斥路线，区别在持续状态、机制贡献和验证。

## 3. 角色、智能形态与权限

**已确认：设备角色、认知能力、行动权限三个维度独立。**
MCU 可独立作为智能硬件，也可作为受控外设。首期标准形态约定：

| 形态 | 角色与职责 | 控制边界 |
| --- | --- | --- |
| 辅助智能 | 下位机，由其他 device 绑定和授权；分析、诊断、建议 | 智脑不自主发起控制，可执行明确授权的上位命令 |
| 模拟智能 | 上位机，自身维护情境、目标和任务，作出决策 | 行动候选经授权、安全、时效与资源检查 |
| 认知探索方向 | 增加世界/身体/自我模型、规划和学习 | 不因能力增加自动扩权 |

这是首期形态的角色约定，不把它固化为所有未来设备的唯一拓扑。
首期上位机只控制自身外设，跨设备控制后续实现。
辅助下位机绑定/受控合同保留，验证端可为测试工具；具体验证方式
待定，不把模拟当成跨设备实机验收。
绑定不等于无限授权；本地安全保护、看门狗和停止独立保留。
建议不得由消费者绕过授权转成动作，同一通道不由多个大脑隐式支配。
控制期限、争用与断联合同待设计，保留现有本地/远程来源仲裁。
学习不自动增加权限，情感不是自主行动前提，记忆也不是授权来源。

### 首期辅助智能参考配置（已确认）

通用性不只靠裁剪后能编译证明：需完成“设备数据 → 分析 →
建议/诊断结果”闭环，不依赖屏幕、摄像头、音频、情感或长期记忆，
不另开发第二个完整消费产品。该配置是框架验收载体，
不是所有辅助设备必须提供相同运行统计的产品要求。

三个必需场景：

1. 授权查询与低风险可观察操作，拒绝未授权请求，安全保护独立；
   控制端可为测试工具，绑定/控制的具体验证与实机范围待定。
2. 设备运行状态助手，使用实际可取得的运行时间、重启原因、错误次数、
   资源使用等输出异常说明和维护建议；字段/数据源待定，
   结果关联依据，数据不足明确未知，不编造故障或寿命预测。
3. 控制端断开、超时、重复及云端故障时显式处置，不扩大权限，
   建议不自动控制。按最新决议，云端不可用时停止智能分析，
   只有满足依赖及授权/安全合同的固定功能或 App 可继续。

两种首期配置共用合同和适用代码，不能用互不相关的固件证明通用性。
Linux 首期可承担必要合同/重放验证，具体范围待定，不等于完整产品。

## 4. 智脑与公共边界

保留智脑层；完整脑是机制交互形成的系统，不是与情感/记忆并列插件。
逻辑职责候选：感知上下文、内部状态、记忆与模型、决策任务、
适应学习。并不要求全部设备装配、立即创建目录或独立线程。
App 适合可交付能力，驱动、临时行为、常驻认知和模型更新不强行
共用加载机制。模块化单体优先，普通函数足够时不新增服务。

| 公共边界 | 已确认方向 |
| --- | --- |
| 必须共享语义 | 来源/有效性/时效、能力/任务/回执、取消/超时/迟到、所有权、错误/未知、权限与安全 |
| 按证据共享代码 | 无平台算法、有界状态机、编解码、规则和测试向量 |
| 平台分别实现 | 调度、并发、内存放置、存储、模型执行、设备/进程恢复 |

不重造跨平台 OS，不逐项包装 RTOS API；只抽取公共逻辑实际需要的
窄接口。MCU 不原样搬运研究的大消息、数据库、检查点和工件系统。
设备内认知与推理后端分离；工程工厂不充当运行时智脑。

### 可选媒体能力与范围控制（19:27 已确认）

**采用“小核心 + 可选媒体扩展 + 平台后端”，不自建完整通用媒体系统。**
完全由产品实现会重复权限、取消、缓冲和恢复，AI App 也难以复用；
核心内置完整媒体管线则扩大格式、状态和平台组合。选择窄能力合同，
把媒体特有的复杂性限制在扩展和后端，不变成所有设备强制依赖。

| 层级 | 职责 | 不承担的职责 |
| --- | --- | --- |
| 通用核心 | 能力发现、授权、依赖、任务、资源、取消、错误与生命周期 | 像素格式、采样率、codec、摄像头初始化 |
| 可选媒体扩展 | 类型化图像/音频操作、格式支持查询、缓冲和时间语义 | 任意编辑、自动格式转换、产品对话策略 |
| 平台后端 | Zephyr/Linux 驱动、DMA、缓存、硬件加速及按需复用已有库 | 角色或自主交互决策 |
| 产品 | 外设装配、触发、表达/对话组合与体验 | 绕过公共合同直接操作共享设备 |

图像、音频、显示/表达可分别装配，不强绑为一个大模块；
共用机制共享，但类型与依赖分别声明。分层不要求新增线程或服务。
ASR/TTS/视觉理解属于推理或服务适配，AEC/重采样/编码属于可选
处理后端，不因使用媒体就全部纳入核心。

首期操作类别方向：

- 图像：查询可用能力、请求一帧、获取结果、取消/释放。
- 音频输入：开始有界采集、获取音频块、停止。
- 音频输出：开始播放、提交数据、查询进度、停止。
- 显示/表达：独立的有限输出能力，不暴露整套 UI 引擎。

以上不是已冻结的函数签名；具体格式、权限粒度、生命周期与后端
尚待设计。不由单帧采集扩成实时视频系统，也不由音频接口扩成完整
语音助手。首期不建设任意动态媒体图、任意格式协商/转换、全部 codec、
混音、多路同步、通用视频会议/播放器或无场景依据的插件体系。

必须保留的合同：

1. 缓冲所有权和释放/复用时机明确。大媒体不塞进通用事件队列，
   不向 Wasm 暴露宿主裸指针；通过受控引用或有界复制访问，
   零复制只是平台优化，不是统一承诺。
2. 采集、处理时间及接收、实际播放进度分开。正常排空结束与取消
   丢弃待处理数据不同，不能把“停止”实现为继续播放全部积压内容。
3. 采集、播放、保存、外发分别约束；采集许可不自动授权保存、
   上传或写入记忆。
4. 格式、帧/块大小、缓冲数量、并发和等待有界；不支持的组合明确拒绝，
   不暗中增加转换、线程或内存。首期优先明确申请/释放，
   不提前建立复杂混音或抢占策略。

接口准入与验收：

- 每个新接口对应明确场景与正反验收，不仅因为“未来可能需要”进入核心。
- 关闭媒体扩展后不链接其驱动、缓冲池或线程，继续通过辅助智能/App
  合同测试；关闭后能编译不是全部通用性证据。
- 统一语义而非全部格式/加速器；公布实际支持组合。
- 测量开关前后固件、RAM、线程、队列和取消/并发行为，验证扩展成本；
  不凭接口少就声称开销低。

现有 `ts/hal.h` 的 AV 接口和 `src/hal/av.c` 已有采集、播放、发布、
格式绑定与摄像头生命周期，是迁移基础，不从零删除重写。
音频/图像共用参数（`w` 兼作采样率）、采集与网络发布、上层合同与
Zephyr 清理逻辑需要重新划分。保留有效行为，分批提取边界，公开 ABI
兼容另审；本轮读取不代表已重新验证实现或通过当前板实测。

调研依据：[Zephyr Video](https://docs.zephyrproject.org/latest/hardware/peripherals/video.html)、
[I2S](https://docs.zephyrproject.org/latest/hardware/peripherals/audio/i2s.html)、
[PipeWire 职责与策略分离](https://docs.pipewire.org/page_overview.html)、
[PipeWire 对象分层](https://docs.pipewire.org/page_objects_design.html)、
[GStreamer 元件](https://gstreamer.freedesktop.org/documentation/application-development/basics/elements.html)、
[队列](https://gstreamer.freedesktop.org/documentation/coreelements/queue.html)、
[线程](https://gstreamer.freedesktop.org/documentation/application-development/advanced/threads.html)。
借鉴分层、所有权和背压，不在 MCU 上重建桌面媒体图，
不照搬其线程/队列默认值，也不据文档声称库已适配当前平台。

### 条件触发的自主思考与受控行动（已确认）

1. **触发**：新事件、任务或内部状态变化、有界周期检查等，在预算内
   启动慢思考；不无限调用，也不每次信号变化都思考。
2. **决策**：结合当前情境、可用记忆、情感和任务，选择不行动、
   更新内部状态、建议或行动候选。
3. **执行**：独立检查权限、安全、时效和资源，再执行并接收反馈。

允许思考不等于允许行动。勿扰通常禁止打扰，不一概禁止内部思考；
关闭、拒绝和打断有效。辅助智能只分析/建议，不借慢思考自主控制。
抽象机制不永久绑定 LLM，但**首期云端依赖策略以下节为准**；
不能引用早期“慢思考未必云端”来伪造首期离线智能。
触发不自动授权媒体采集或上传。

### 时间与评估（已确认）

- 单调时间用于期限、安全与冷却；日历时间用于日期/证书/日程，不用
  可跳变墙钟计算控制超时。
- 采集、接收和处理时间分开，旧数据不冒充现在；媒体可用采样序号，
  必须声明时钟对应关系。
- 逻辑步骤不等于现实经过时长，衰减明确 dt 或实验虚拟时间。
- 跨设备 uptime 不直接相减，声明时钟域、启动标识、不确定性和有效期；
  定义重启、睡眠和回绕。
- 高分辨率不保证回调准时；确定性状态机可重放，模型按语义/误差验证，
  不强求不同平台浮点逐位一致。

整体认知效果保留人工评估；机制贡献用消融、注入和重放对照，
工程可靠性自动测试。加入模块说明问题、影响与观察方式。

## 5. 记忆能力：框架机制与配置要求分离

**已确认方向：**参考 Galatea，支持经历积累、巩固、遗忘和经历驱动
的角色发展，引入 LLM 定期优化。详细记忆架构后续设计，不一次承诺
全部人类记忆、完整预测脑或在线权重学习。
记忆类型与保存合同分开：工作上下文、设备统计、经历、模型参数。
性格发展、强制 TF 配置及缺卡产品行为见[产品记忆定义](p05-first-product.md)。
桌面产品及启用经历记忆的配置要求大于 8 GB TF；辅助配置可不需要，
不能推广为全部模拟智能或所有平台的最低存储要求。

**设计建议，未冻结：**RAM 工作记忆/缓存、持久经历/索引/版本；
单写者、来源/可靠度、情感有界调制；LLM 生成巩固候选，再检查来源
和结构后提交；不把用户陈述/推断/想象晋升为亲历。
保存可恢复版本、调度与写入预算，不全库扫描或每次情感更新落盘。
内置 Flash 可存小状态但不承担大量经历；外部容量不解决工作内存。
衰减、抽象、认知遗忘与用户删除不同；删除须涉及派生内容和缓存，
谱系不凌驾删除，不保证普通文件删除后物理不可恢复。
恢复不复活被删内容，损坏不静默格式化。云端巩固需单独外发授权；
不自动保存音视频、全部会话或用诊断日志构造亲身经历。

## 6. 云端依赖、App 与离线恢复

**18:33 修正早期建议：首期强依赖云端 LLM，算力不可用时辅助智能
与模拟智能停用，不能用本地规则冒充离线智能。**
保留产品声明的固定功能、安全保护和本地停止，不清空已有记忆。
未来原生本地推理配置不由此被永久禁止。
**18:37 补充：AI 创建的 App 按实际依赖运行，不因创建者是 AI 全停。**
例如本地计时仅依赖时钟和提醒可继续；持续云分析失去模型则不可继续。
蓝牙播放只是另一产品的例子，不是框架或首个产品必需能力。

已确认的运行与恢复原则：

- 安装兼容性、运行依赖和权限不同；网络权限不代表网络或具体模型可用。
- App 持续检查依赖，并预先声明未启动拒绝/等待、运行中暂停/停止/失败、
  资源与输出清理；只允许已声明和验证的子集降级，不由 AI 临时猜测。
  是否细化为阶段/能力级依赖待设计。
- 网络、模型超时、凭据/额度与恢复验证分开；单次超时不要求全设备抖动，
  受影响任务及时处置，停用/恢复防抖与重试有界，阈值待定。
- 取消在途云端思考、候选、对话和巩固，拒绝迟到输出；
  固定功能和独立 App 依赖满足且权限/资源/任务状态允许才继续。
- 取消、静音、关闭自主交互重连后仍有效；未知非幂等动作不盲目重试。
- 恢复先验证服务、核对设备/任务、恢复允许的能力，再后台分析日志。
  不自动续跑旧动作，日志不阻塞正常恢复，不自动修改代码/权限/安装。
- 现场日志必须保存且有界：时间域、故障、依赖变化、App/任务、资源和
  处置结果；容量、保留期、脱敏与外发待定。失败显式报告且不阻塞停止，
  重连不自动上传全部日志。辅助配置可用非 TF 的有界存储。
- 恢复检查全部必要依赖；某一依赖恢复不代表整体可用。
  存储故障行为按配置定义，不将产品缺卡规则推广到所有形态。

AI 新建可交付能力封装为 App，不要求每句请求都重新生成 App；
已有能力调用/配置的任务包装待定。智脑、记忆、安全及驱动不全部 App 化。
现有 manifest `needs` 是资源/兼容合同，不代表动态网络/模型依赖已实现。

## 7. 新能力交付与用户验收

### 交付职责分层（19:09 接受建议，具体接口待设计）

- 需求与目标约束：声明目标设备、接口、权限、依赖、资源与验收条件；
  缺能力明确拒绝/反馈，不让 AI 编造接口。
- 工程工厂：生成候选，执行构建、合同和适用行为验证，提供真实证据。
- 设备交付管理：设备侧完整性、验签、兼容与资源检查，保存候选、
  版本与晋升；不能只信工程端报告。
- App 运行管理：试用执行、依赖、资源、停止和故障处置。
- 验收授权：验证确认来源，并绑定具体候选内容、权限及目标；
  AI 不代替用户批准，修改候选不能沿用旧确认。

上述是逻辑职责，不要求各建一个线程或服务。状态所有权、协调、
试用数据隔离、槽位、确认凭据、超时与掉电恢复尚待详细设计。
框架不规定必须通过屏幕、语音或手机确认；正式安装也不等于
立即运行或自动启动，启动条件另受运行合同约束。

### 显式开发/测试配置例外（19:09 用户明确确认）

允许以下开发便利，**仅限显式开发/测试配置**：

1. 可直接部署、试运行候选，不必每轮走产品级用户试用验收；
   不等于把候选自动晋升为已获用户确认的正式产品版本。
2. 框架可以提供超出首个验收产品范围的能力接口，不以产品功能清单
   封死通用接口；不意味着立即实现所有能力或宣称已支持未验证硬件。
3. 可提高 App 资源预算和试用时限，但仍声明并执行明确上限，
   实际平台资源与安全约束仍有效。

正式产品仍遵循完整交付合同。上述例外不授权关闭验签、权限、
受保护输出、取消或恢复机制，也不授权真实外发、硬件操作或付费调用。
开发配置和候选需可识别，不能静默成为生产默认；开发直部署成功

从开发候选进入正式产品流程时，仍须完成对应工程验证、受控试用、
具体版本的用户确认及设备检查。配置门控和标识实现待设计。

## 8. 九类框架保证与架构分层（18:55 已确认）

保证仅适用于明确支持的平台、配置与预算，不是安全认证或已验收结论。

| 类别 | 框架必须保证 | 正反验证 |
| --- | --- | --- |
| 配置与能力 | 声明形态/角色/能力/预算，必要能力缺失拒绝，可选模块不产生假成功；支持/可用/获准使用分开 | 裁剪、缺失、兼容、权限、变化 |
| 依赖与降级 | 持续检查，预先声明失效/恢复，全部必要依赖与执行条件满足才运行 | 断网、模型、凭据、存储、抖动、并发故障 |
| 执行与授权 | 思考/决策/执行分离，受保护输出不可绕过，辅助不自主控制，模拟候选经检查 | 越权、过期、争用、建议误转动作 |
| 任务与回执 | 身份关联和明确状态，完成/失败/取消/未知不混同，阻止迟到和失效输出，重复按合同处理 | 乱序、重复、取消竞争、超时、重启、丢响应 |
| 资源与调度 | 计入宿主的预算，队列满有策略，停止不被无限阻塞，超限拒绝或显式降级 | 内存不足、积压、慢调用、长执行、泄漏 |
| 故障隔离 | App/共享服务/系统故障域明确，各自清理、限制影响或按平台合同安全处置/重启 | 故障注入、恢复、实际隔离范围 |
| 安装与恢复 | 验证/试用/确认/晋升分离，设备验签/兼容，内容绑定确认，中断不误晋升，代码/数据恢复分开 | 坏包、错签名、内容变化、试用失败、掉电 |
| 数据与观测 | 来源/有效性/时间域，有界可关联日志，凭据不进普通日志，授权保存/删除/外发，记录失败不阻塞安全 | 满/坏存储、来源、删除、外发边界 |
| 验证与兼容 | 共享合同向量、适用平台测试，确定性逻辑可注入，版本/迁移明确，各证据状态分别报告 | 跨后端、升级回归、证据完整性 |

边界：取消不撤销已发生效果，无观测不证明物理完成，通信不保证
端到端恰好一次。Wasm 不隔离所有宿主/原生驱动错误；各平台公布实际
强度，不能默认当前板启用用户态。指令预算不等于固定耗时，
阻塞宿主另约束。认知判断/LLM 输出不保证永远正确或逐字确定。
不承诺全芯片、任意组合或任意故障不影响设备。

**已确认架构阶段提前合理分层：**依赖、任务、资源、故障、恢复和
观测是关联但不同职责，不能堆进万能管理模块或事后补边界。
设计需明确状态所有权、依赖方向、输入输出、故障域和跨层协调，
再决定目录/批次。分层不等于新增线程、服务或 App，不重复状态机；
具体层数、模块名与接口尚未冻结。

每项保证保存“合同 → 实现机制 → 正反测试 → 证据与适用范围”。
基础硬件验证、框架联动验证、产品验收分开；编译/模拟/实机、
跳过/未运行/通过分别报告。数值按平台配置验证，产品评价是否满足体验。
升级重跑受影响关卡，不继承未经验证结论。

## 9. 基座选型：修正过程与最终方向

最初针对 P4/C5 多媒体偏向 IDF；用户明确媒体可选和未来跨厂商后，
**已修正并确认 Zephyr 默认 MCU + 原生 Linux ARM64/x86**。
不整体迁 IDF，不把框架等同 Zephyr API；具体产品关键缺口可评估
例外后端，不现在维护两套完整 MCU runtime。
迁移涉及锁、事件、存储、看门狗、WAMR 和测试，不是换头文件。

多厂商、裁剪、硬件接口和主机回归符合长期方向；ESP 新组件可能
更直接，但不存在可靠同板同负载证据证明任一 RTOS 普遍更快。
STM32N657、RT700 等说明外部 RAM/Flash 与算力不只存在于 ESP；
硬件有 NPU/DSP、Zephyr 有板定义不等于驱动已验收。
zDSP 优化因架构不同，允许厂商后端；ESP-NN 优化算子数据不是 OS 对照。
PSRAM 不替代内部 RAM，DMA/对齐/缓存/栈/Flash 限制分别验证。
基线比较固件、内部/外部 RAM、峰值、连续空闲块、栈、吞吐、
P95/P99、取消、恢复以及适用能耗和写寿命。
同板统一功能/频率/编译/内存/保护；跨芯片比较任务成本和能效，
阈值先于结果确定，不用关闭保护制造性能。
IDF host 模拟不作为 Linux 产品运行时；上游 WAMR 支持仍需固定版本
复验，IDF OTA 不替代 App 交付，Zephyr HAL 不让任意 IDF 组件直接可用。
