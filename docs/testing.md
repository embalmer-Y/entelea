# 测试与验证范围

本文面向贡献者。环境准备见[开发指南](development.md)；普通验证不刷写设备
或调用付费模型。

## 2026-11-06 阶段边界调整

用户已将 P04 收敛为当前 `68007` 的显示、触摸、扬声器、麦克风、
SC2336 成像及 SD 文件系统/文件读写独立验证，按本页现有证据完成。
这不是补测或把失败改判通过：隔离音频候选、IDF 相机预览和有限交互的
限制仍然有效。正式产品接入、复杂生命周期、硬件联动及既有 App 测试
转入新增 P06；新增 P05 为工程重整，原 P05–P17 顺延为 P07–P19。
当前板 SD 物理拔插仍不在范围内，C5 网络仍属 P03，H0 未验收。
详见[当前阶段范围](requirements.md#2026-11-06-开发阶段调整)。

下文较早实验记录中的“P04 未验收”及“P04/H0 未通过”等表述保留当时的
旧范围，不代表新 P04 节点仍未完成；相关产品缺口现由 P06/H0 承接。
后续硬件相关变更仍需在当前板真机验证，不能用此次改排替代实际验收。

| 入口 | 范围 | 限制 |
| --- | --- | --- |
| `make check` | 仓库、Python 回归、安全机械检查和情感内核主机测试 | 不验证板卡 |
| `make firmware-build` | native_sim 固件构建 | 不是交叉编译板级镜像 |
| `make firmware-test` | `firmware/tests/` 下有 `testcase.yaml` 的 Twister 自动套件 | 不自动执行手动板级实验 |
| `make firmware-p4-build` | 固定 P4/C5 板上的框架交叉构建，准备见[开发指南](development.md#esp32-p4c5-交叉构建) | 仅生成镜像；不验证 C5、外设、部署或目标板时序 |
| `make firmware-p4-store-build` | P4 独立 flash 存储配置的交叉构建，保留 RAM 基线 | 预留分区拆分已批准开发，但不授权烧录；物理 flash 恢复仍需 H0 |
| `make firmware-p4-net-build` | 固定 P4/C5 无凭据扫描诊断交叉构建 | 不访问串口；不证明关联、DHCP、DNS、TLS、传输或重连 |
| `make firmware-p4-tls-build` | 独立 TCP/DNS/严格 TLS 与故障恢复诊断交叉构建，Kconfig 警告即失败 | 不访问串口；编译不能替代实际网络验收 |
| `make firmware-p4-sd-build` | 独立 P4 SD/FatFS 诊断交叉构建，Kconfig 警告即失败 | 不访问串口；实际运行会在 SD 上创建并删除测试文件 |
| `make firmware-p4-touch-build` | 独立 P4 CST820 事件诊断交叉构建 | 不访问串口；实际运行会启用持续轮询，结束必须换回非轮询固件 |
| `make firmware-p4-display-build` | 独立 P4/CO5300 显示诊断交叉构建 | 不访问串口；真实图案、DMA 长度、关屏与人工视觉必须另行验证 |
| `make agent-test` | Forge 全量主机测试、跨仓库夹具及 Skill 同步 | 部署与仿真 E2E 按其显式条件启用 |
| `make style BASE=<commit>` | 相对基线新增或修改的第一方 C/H 文件 | 不覆盖导入基线的全部风格债务 |

`firmware/tests/board/` 保存需要对应板卡或其他专用环境的实验工程；每项的
实际适用板、配置和判据以工程内容为准，不能把它们计作 CI 已执行。`netlab/`
用于需额外网络配置的仿真部署；`pytest/` 与 `safety_check/` 为主机检查。
[板级工具说明](../tools/board/README.md)列出运行风险和先决条件。

`core` 套件包含以下独立配置，正常 core 配置不使用链接替身：

- 启动失败配置使用链接替身，验证初始化、通道耗尽、非法结果以及重试
  不重复初始化。
- 硬件后备配置使用真实 Zephyr task watchdog 和测试设备的驱动 API，
  验证安装/启动错误、失败不喂硬件、重试不泄漏通道、启动成功及通道满。
  还执行实际框架启动函数，确认失败后输出进入故障态、后续步骤不执行、
  不发布启动完成。
- 硬件未就绪与必需节点缺失分别验证拒绝启动，不以软件后备冒充硬件可用。

`periph` 的独立注册失败配置验证外设/安全类型不一致和 HAL 容量耗尽均不
留下安全通道、供电槽或可见的外设半注册；注册链按单初始化线程合同执行。
这些测试验证软件控制流及仿真状态，不证明 P4 引脚、物理输出或复位时延。

## Galatea 情感参考回归

`make affect-test` 先检查[固定数值参考](../lib/affect/tests/reference/galatea.py)
与生成夹具一致，再编译并执行原有 C 测试及
[共享算子回归](../lib/affect/tests/galatea_reference.c)。
覆盖低通阶跃/衰减、迟滞边界和连续效价轨迹；效价测试直接调用真实
`ke_step`，不以测试版 C 公式代替生产实现。

参考不依赖原 Galatea 工作区、PyTorch、网络、设备或真实媒体。只检查
共享算子，不能验证社交驱力、伦理闩锁、重评价和完整研究系统等价，也不能
替代 P11/P14 的下游影响、禁用和硬件验证。夹具使用 float64 参照和
`1e-6` 绝对误差比较 float32 输出，不要求跨精度 bit-exact。

Python 回归检查生成确定性、夹具一致性以及修改/缺失夹具的显式失败。
改变参考或向量时先核对[固定来源](provenance.md)，再用
`.venv/bin/python lib/affect/tests/reference/galatea.py` 生成候选内容，使用
已有锁定的 clang-format 格式化 C 输出；不能改期望值
掩盖 C 行为回归，也不自动跟随研究仓库最新版本。

## 媒体与 SD 验证

[P4 触摸芯片识别](../firmware/tests/board/p4touchid/)只读取 I2C0 上
`0x15` 的 `0xa7` 寄存器，不配置触摸复位脚或点亮屏幕。
[替身回归](../firmware/tests/touch_id/)检查指定地址与寄存器、`0xb7`
成功、其他 ID、总线错误、未就绪总线和空输出参数。识别 ID 不验证触摸
事件、定位、方向或显示。用户提供的屏幕资料列出 CO5300、MIPI 和
460×460，但触摸字段未填写；历史样板曾识别 CST820，不代表新板。
历史资料将 GPIO6 标为触摸复位，核心板连线图还标出该脚连接 C5 GPIO2；
历史注释称其为握手，实际用途和复用待核实，未经确认不得操作该脚。
固定 Zephyr 的 CO5300 MIPI 实现包含 NXP 平台耦合，初始化还设置最高
亮度；不能直接在 P4 上将其作为安全的点屏方案。

新主力板（串口尾号 `67689`）经用户确认单 USB 供电、排线方向和当前
复位安全后，P4 完整预写快照与上次已验证扫描镜像状态一致。经授权仅擦写
`[0x2000,0x25000)` 运行识别诊断，独立 16 MiB 回读确认镜像、扇区尾部
擦除字节及范围外所有字节符合预期；原厂 Flash 备份仍私有保存。
三次受控运行均报告 `P4TOUCHID PASS id=0xb7`，未点亮屏或操作触摸复位脚。
首次启动先出现一次 `HP_SYS_HP_WDT_RESET`，随后才进入诊断并通过；另两次
复位直接进入诊断。此前同板两个扫描日志也出现过同一先复位现象，
原因未定位，不能宣称启动稳定性已通过。当前板运行此诊断而非扫描固件；
ID 读取不验证真实按压、坐标、方向、显示、触摸与 C5 共存或整机安全态。

[触摸事件诊断](../firmware/tests/board/p4touch/)先识别芯片，延迟初始化
Zephyr CST8xx 轮询驱动；事件状态机的[替身测试](../firmware/tests/touch_events/)
覆盖按下、移动、释放、重复状态、坐标越界、缺帧及异常输入。它会修改触摸
控制器运行时寄存器；报告结束后轮询驱动不会自动停止，须刷回非轮询固件。
软件回归不能替代触摸验证，观察到事件后仍需对照人工操作确认位置和方向。

用户同意运行时触摸寄存器配置并协助触摸。新板使用上述轮询配置、
不启用显示或网络：首轮收到三组按下/释放，随后出现坐标越界
（`-ERANGE`）而停止。该次镜像未打印越界时的坐标，无法据此确定原因。
重启后第二轮用户按中心、上、下、左、右操作，收到五组按下/释放，坐标
方向与该顺序一致。它只证明此次简单交互，不证明边缘、连续滑动、长期
稳定性、错误恢复或 C5 共存。诊断随后增加越界时的坐标日志并完成构建，
后续带此日志的真机复测见下；不得把第二轮通过解释为首轮异常已经解决。
事件镜像按 `[0x2000,0x26000)` 擦写，最终刷回不持续轮询的识别诊断，
其擦写范围为 `[0x2000,0x25000)`；独立整片回读与预期逐字节一致，
范围外保留此前内容，其中部分旧事件镜像字节仍留在 Flash 中，但位于
恢复镜像的结束标记之后。恢复后单次启动再次读取 `0xb7` 成功。

本轮重新确认当前 `67689` 是 P4 v3.2、16 MiB Flash，完整预写快照与
非轮询识别镜像一致，并由 esptool 独立摘要校验；各次写入后整片回读，
逐字节核对镜像、扇区尾部及范围外保留内容。带异常坐标日志的事件镜像
先连续两次无法建立空闲基线，第二次已由用户确认无接触；增加只读寄存器
快照后，初始化前后 `0x00..0x06` 都为零。原驱动忽略零手指数而将事件
位零判为按下；获批的[报告补丁](../patches/zephyr-cst8xx-report.patch)
修复此问题。[真实驱动回归](../firmware/tests/touch_driver/)经 I2C
模拟总线覆盖 6 个用例，另有事件、识别及 SD 回归合计 **17/17** 通过。
这些仍是主机回归，不当作真机证据。

补丁后真机成功建立空闲基线。一次人工未及时操作的轮次在 0/5 超时，
明确不计通过；重启后按中心、上、下、左、右实测五对完整按压/释放，
按下坐标依次为 `(176,275)`、`(189,74)`、`(189,406)`、
`(33,249)`、`(376,249)`，方向与用户操作相符。另一轮用户实际进行了
上、右、下、左四边滑动及中心画圆，五组都有移动及释放，轨迹与操作
相符，未观察到越界。此操作与预定的边缘轻按及水平直线不同，不能记成
未执行的用例；也没有覆盖坐标端点、长时负载或 App 输入。
五点轮启动前再次出现 `HP_SYS_HP_WDT_RESET`；本次简单交互通过
不证明历史越界已根治，启动稳定性及 C5 共存仍未通过。

[低亮度显示诊断](../firmware/tests/board/p4display/)不驱动复位脚，
使用通用 DSI 主机/扫描控制器，前三轮普通与 HBM 亮度均限制为 8/255。
首次实测因本次配置遗漏 PSRAM/MPLL 的 LDO2 1.8 V，启用稳压器驱动后
HAL 不再代管该电源，PSRAM 初始化失败并发生 CPU 异常，未进入点屏程序。
补齐 LDO2 常供并开启内存自检后，真机识别 AP 256 Mbit（32 MiB）
PSRAM、200 MHz，并进入显示诊断；但首个 15 秒阶段的帧完成计数为 0，
诊断显式失败并执行关屏流程。用户观察为始终黑屏、无异常发热。
该轮显示未通过，不能以命令返回或成功识别 PSRAM 代替显示验收；
同次启动也重现了上述看门狗额外复位。

第三轮仍为 0 帧；只读快照后额外运行 10 秒主机内部彩条隔离，
明确标记 `acceptance=0`。用户看到微亮近单色、无异常发热，并非正确
彩条确认，诊断仍报告失败。随后定位到扫描驱动把对齐分配长度
423,232 字节误作 DMA 帧长，多于真实像素的 423,200 字节。
获批的[帧长补丁](../patches/zephyr-p4-dsi-frame-size.patch)保留分配/缓存
对齐，仅将真实像素长度用于 DMA，并拒绝不能按 64 位完整传输的帧长。
修复后第四轮 RGB 竖条及红绿蓝白四分区各 **448 帧/15 秒**，
均超过 150 帧门槛，实际 DMA 寄存器均为 **52,900 个 64 位单元**，
没有传输额外填充，最终输出 `IO_OK`。用户确认两种图案正确、最后熄屏，
无异常闪烁或发热；亮度 8/255 过暗，不便观察。
该轮采集脚本误用不存在的 `DONE` 结束标记，尽管已收齐最终 `IO_OK`，
仍超时退出；不隐去这一采集错误，也不将其记为显示程序失败。
第四轮启动前再次出现 `HP_SYS_HP_WDT_RESET`，启动稳定性仍未通过。
用户随后批准普通亮度提高至 32/255 复测，HBM 保持 8/255 且不开启
高亮模式。第五轮两种图案仍各 **448 帧/15 秒**，DMA 仍正好
**52,900 个 64 位单元**；最终 `IO_OK`，采集使用正确结束标记正常退出。
用户确认两种图案的颜色、方向和位置正确，亮度便于观察，最终熄屏，
无异常闪烁或发热。受控显示诊断两轮通过，但第五轮启动前也发生
额外看门狗复位；不能据此接受启动稳定性、长时负载或 App/媒体联合功能。

显示阶段主机 `make check` 为 **166 项 Python 测试**及情感、安全机械检查通过，
其中依赖准备/构建接线回归 **72 项**；触摸驱动、事件、识别及 SD 的
focused Twister 再次 **4 配置、17/17 用例**通过，无警告。
显示 P4 镜像构建、其 C 文件格式与严格 checkpatch 均通过；
本轮未重新执行完整 `make firmware-test`，不将历史全套结果充作本轮结果。
额外执行的 `test_env_installer.py` 全文件 Ruff 格式检查仍有既存格式债务，
在未修改的 HEAD 版本同样失败；未重排整个历史文件，Ruff lint 与测试通过。

显示阶段结束时从最初快照恢复全部触及的 `[0x2000,0x38000)`，包括较大
诊断镜像的残留范围，而不是只覆盖较短的识别镜像。独立读取整片
16 MiB，与本轮最初备份逐字节完全一致；随后复位启动非轮询识别固件，
再次得到 `P4TOUCHID PASS id=0xb7`，该次没有额外看门狗复位。
这一单次正常启动不抵消前述额外复位证据。当前无触摸轮询、显示测试
或串口采集在运行；未升级 C5、调用云模型或保存/外发原始媒体。

### P4 早期启动复位追踪

**当前归类：原板 `67689` 硬件问题，疑似 DCDC 供电链路异常。**
2026-11-05 用户转述交流群中有其他人遇到相关问题，更换 DCDC 后
恢复正常；这是第三方反馈，尚未经本项目独立核验。原板最后可见
的 IDF 启动标记位于 DCDC 交接入口，且相同 hello 在新板未复现，
与这一怀疑方向相符，但都不能单独证明具体器件根因。原板尚未更换
DCDC，也没有更换前后对照、停核 PC 或供电波形；故该板故障仍未
修复，不能把 DCDC 器件损坏当成已确认事实。新板 `68007` 继续作为
P04 主力，不把原板故障当作新板已复现的问题。

后续独立复测原非轮询识别固件，三次受控复位中 **2/3** 出现额外
`HP_SYS_HP_WDT_RESET`；默认关闭的
[ROM 启动包装](../firmware/tests/board/p4touchid/src/boot_trace.c)在三次
粗标记运行中均将复位收窄至 `bootloader_clock_configure()` 内。
经批准补齐 CPLL 配置调用后，真机仍失败；打开内部细 UART 的两次
直接启动只能证明时序被改变，不能记为修复通过。

低输出候选镜像两次捕获看门狗前的非法指令异常：
`cause=0x30000002`、`pc=0x4fc012fc`、`mtval=0x4ffc07f7`。
官方 esptool 只读取得该 ROM 地址的实际字为 `0x4ffc07b7`，与陷阱值
不同；这尚不能证明时钟、取指或供电中的哪一项为根因。
进一步三次候选运行中一次捕获访问异常：
`cause=0x30000005`、`pc=0x4ff2299e`、`mtval=0x55de7ae8`，
其余两次直接启动。精确部署 ELF 中该 PC 对应后续 APB 分频设置区间的
`and` 指令，不能将静态指令和异常类型不一致直接解释成正常总线访问失败。
RTC 记录为 `D- delay_index=4 delay_us=10`，并在随后真实看门狗复位后
原样读出，证明这一阶段记录确实保留；最后检查点位于供电交接的第四次
延时返回，不等于已经证明电源根因。原先只判断 `SYS_RWDT` 的诊断
没有匹配实际 `CORE_MWDT`，未输出记录不能被解释为 RTC 保留失败。

CPLL 候选已从准备/构建默认路径隔离，本项目 HAL 恢复固定提交的干净
源码；不把未通过真机的候选发布为修复。使用相同低输出包装的干净 HAL
对照在三次受控复位中均直接启动并读取 `0xb7`，未捕获异常；这三次

#### 68007 AHB GDMA 换通道对照（2026-11-05）

固定 Zephyr 的 AHB 控制器声明 6 个逻辑通道，成对对应 3 组物理
RX/TX：`0/1`、`2/3`、`4/5`。隔离诊断不启用 I2S，依次以每个逻辑
编号配置一次 M2M，分别测试 burst 参数 `8` 和 `16`。每次运行期生成
256 字节非空数据，检查完整目标和源数据、64 字节越界保护区，并分别
等待 RX 与 TX 完成回调；超时为 2 秒。下表为两次独立 EN 的结果：

| 物理通道组 / 配置编号 | 两种 burst 的结果 |
|---|---|
| 0 组 / `0`、`1` | 两次均无 RX 或 TX 回调，目标数据不匹配 |
| 1 组 / `2`、`3` | 两次均收到 RX 和 TX 完成回调，数据、源及保护区均正确 |
| 2 组 / `4`、`5` | 两次均收到 RX 和 TX 完成回调，数据、源及保护区均正确 |

每次 EN 均为 8/12 组合满足上述完整判据；缓存操作和停止均返回成功。
因此另两组在**此独立、短数据、串行配置**下可用于 M2M，但未验证
并发争用、长时负载或 AXI 控制器，不能视为 RX0 已修复。此前 TX 5
的测试报告保留；此次额外明确检查了两个方向的完成回调。

随后使用仓库的 16 位 I2S 数据回环，在未修改 GDMA 的独立构建中，
分别将 I2S 从默认 `0/1` 改为 `2/3` 和 `4/5`。两种配置各两次 EN
均在首块第 2 帧报告 `expected=3002 got=3002/3100`；因此换组不能
解决这个独立的 I2S 基线错误，未改动产品板级通道配置。

目前已检查的 P4 I2S 驱动使用外设到内存/内存到外设方向，项目固件中
未发现直接使用 M2M 的调用；结合以上其他通道结果，**将 AHB 第 0 组
M2M 异常标为等待社区上游修复，不再单独作为继续 P04 的前置条件**。
这不保证未来相机或联合负载不依赖该路径；若引入 M2M 或通道冲突，
须重新评估并实测。I2S 驱动数据错误、正式音频接入及生命周期仍须解决，
不能因 M2M 状态调整而记为通过。

三种镜像均构建并经官方写后校验，最后恢复先前 hello 的
`[0x2000,0x3a000)` 范围并校验，独立 EN 正常、串口释放；未做独立
整片回读。此次只记录合成 DMA 数据的比较结果，没有采集真实音视频。

#### 68007 音频外部刺激与人工遮挡（2026-11-05）

#### 68007 I2S 普通停止与重启（2026-11-05，独立诊断）

PCM16 都先清理旧视频流；失败不提交新绑定。绑定、采集及放音串行化，

[App 启动回归](../firmware/tests/app/src/av_boot.c)另有 2 个用例，

## C5 扫描与网络验收

此前的实际 C5 扫描与网络证据属于 10.1 寸板；新主力 2 寸 AMOLED 板必须
重新验证实际运行结果，不能继承原板验收。

新主力板 C5 的 4 MiB Flash 已两次独立读取并比对，原始备份私有保存。
经授权写入 Kaleido 留存的 ESP-Hosted 3.0.10 v661 成套镜像，独立全片回读
确认镜像、擦除区域与范围外数据符合预期；原厂分区及部分配置被覆盖。
写入后启动命令已执行，但 C5 串口 15 秒无输出，不证明启动成功。新板
P4 的既有厂商测试固件随后观察到 C5 SDIO 初始化事件及 WLAN 能力；但同一
观察中 P4 曾发生异常复位，host 报告 2.12.0 与协处理器报告 3.0.0 不匹配，
并出现 SDIO 收包、RPC 和 Wi-Fi 错误。日志中的版本报告不能替代镜像构建
标识。随后授权刷入 Entelea 扫描诊断：P4 的 16 MiB Flash 经两次独立备份，
写后全片回读确认镜像和授权范围外数据；两次复位各完成两次扫描，均返回
成功且有结果，C5 报告 v3.0.10。但每次 P4 启动均报告 SHA-256 比较失败；
当时仅能确认扫描路径。

对修复前 P4 镜像的离线检查显示，RAM-only 头的摘要标志为 0，ROM 日志的
计算值等于该 RAM 镜像的 SHA-256，而日志的期望值等于其后 32 字节而非
附加摘要。固定 esptool 对 RAM-only 模式明确不附加摘要。经授权补齐 RAM
摘要和项目内 loader 兼容后，新板三次有效镜像启动均无该警告，各通过两次
扫描；仅翻转摘要一字节的对照镜像使 ROM 报告预期的摘要错误，但 ROM
明确继续启动。随后恢复有效镜像、独立全片回读并再次完成扫描。
这验证当前 RAM 摘要的生成和错误可观测性，不验证 ROM 段或镜像签名，
更不表示摘要错误会阻止启动；新板关联与联网仍未验收。

[扫描诊断回归](../firmware/tests/scan/)通过真实 Zephyr `net_mgmt` 和事件派发，
使用测试 Wi-Fi 驱动及看门狗启动替身执行实际诊断入口。覆盖连续扫描、重复
注册/释放回调、看门狗失败、请求失败、无完成事件的 15 秒上界、完成失败、
空结果及失败后的迟到事件。它不测试 SDIO、实际 C5、RPC 解码或 nanopb
分配失败；不能以该替身宣称真实驱动错误路径已完整验证。

实际板卡运行[无凭据配置](development.md#无凭据-c5-扫描配置)时，
成功必须同时出现两轮 `SCAN_RETURN rc=0`、`SCAN_DONE status=0 results>0`
及 `P4N PASS scans=2/2`，且没有 RPC/扫描超时；复位后重测并记录 C5 实际版本。
空结果只表示本次“现场存在 AP”验收条件不满足，不单凭此断定驱动损坏。
驱动先以非阻塞 RPC 启动扫描，再有界等待 20 秒；诊断的 15 秒是请求成功
返回后等待 Zephyr 完成回调的另一上界，不能当作整个扫描的时间预算。

发生错误立即停止并复位后重新验证，不用下一轮结果抵消失败。
这不宣称已支持运行时扫描取消、并发扫描或扫描超时后的无复位恢复。
运行时联网入口见[开发指南](development.md#tls-能力与运行时联网诊断)；
Wi-Fi/IPv4 不同层的事件不能并入同一个回调掩码，否则回调被过滤。
关联成功必须有完成事件，DHCP 成功必须有真实绑定事件和绑定状态；
主动断开再连不等同于外部断网恢复，不能用请求返回值代替上述观测。
P03 还须区分受控传输故障与外部无线断网，验证完整驱动错误路径和恢复；
真实模型另属 P13。当前证据与缺口只在
[总进度 DEV-07](requirements.md#设备基础和硬件能力)维护。

### 受控 DNS/TLS 判据

[网络探针](../tools/board/p4_net_probe.py)需要明确授权目标、测试网络和本机
服务；它只复位和配置，不烧录。协议见[开发指南](development.md#tls-能力与运行时联网诊断)。
主机证书预检不能替代板卡握手；必须在两个关联/DHCP/断开循环中同时满足：

- DNS 关闭缓存，正向结果只有一个且精确等于授权端点 IPv4。负向必须是
  主机实际发出的 NXDOMAIN；固定 Zephyr 对零 answer 回复映射为
  `DNS_EAI_FAIL=-4`，不是 `DNS_EAI_NONAME`。不能把任意 DNS 错误当通过。
- TLS 始终要求验证 peer 和 hostname；证书回调只观察、不清除验证 flags。
  有效连接必须实际执行验证且 flags=0，每次回显四帧、每帧 256 字节，
  双向逐字节一致。
- hostname 不匹配、不可信 issuer、真实过期证书均须连接失败，验证回调
  确实调用且 flags 分别精确为 4、8、1。普通连接失败不能冒充证书拒绝。
- 主机实际记录两次受控半开握手；固件必须返回 `ETIMEDOUT`、验证回调尚未
  调用，实测连接时长为配置的 10000 ms，允许 -100/+2000 ms 调度/测量余量。
  随后以新连接重新验证证书并精确回显。
- 主机实际记录两次已认证会话的主动关闭；客户端必须观测 EOF，不接受
  任意接收错误、超时或错误数据，并再次以新连接验证和回显。
- 每个循环三次有效回显，共六次/24 帧/6144 字节；三类证书拒绝各两次，
  超时及 EOF 各两次，关联、真实 DHCP、断开各两次。任何失败、FATAL、
  loader 错误、服务错误、重复/缺失标记或清理失败均阻止成功。

DNS 期限 3 秒、TCP 建连 5 秒、TLS 握手 10 秒、每次精确收发 5 秒；
收发使用整体期限，不因部分数据到达无限续期。超时/EOF 恢复是受控服务端
故障，不是 AP 断电、真实无线失联恢复或完整 Zenoh/模型会话验收。
复位后重复同一负载并保留失败证据；有栈哨兵的复测通过不能证明此前 CPU
异常根因已消除。栈使用观测应报告实际负载，不推广为完整产品的内存预算。

[主机探针回归](../firmware/tests/pytest/test_p4_network_probe.py)覆盖二进制协议、
DNS 响应、日志脱敏、真实本机证书验证、一次性故障控制、EOF/回显恢复和
服务清理。它不执行设备端 C；native `net`/`scan` 套件也不能替代新
`network.c`/`tls.c` 的全部驱动/分配/取消错误路径测试。

## 板级基础验收

[镜像生成回归](../firmware/tests/pytest/test_p4_image.py)验证 RAM 摘要与
8 字节结束标记、扇区对齐/非对齐、填充不足/非零、RAM 校验和及摘要损坏、
坏段/截断、段数/分区上界、重复处理及失败时保留原文件；真实板卡 CMake 钩子通过主机最小工程验证
生成顺序、检查器修改触发重生成以及非 Simple Boot 不改镜像。
固定 P4 的五种构建均经 esptool 检查摘要及 ROM 段对齐；新板真机正反验证
范围见上文。旧板标记后存在旧零残留的历史验证不能替代新板完整 H0。

P02 的目标板关卡仍需在 H0 执行：正常启动、停喂与硬件复位、现有分区
核对和备份、flash 掉电/损坏恢复、App 重启恢复及审计。仅屏幕/喇叭的首批
设备没有机构、外部受控供电或专用急停，不报告这些通道的物理验收通过。
历史 `wdtbench` 的协作线程自旋仅验证软件 task watchdog，不证明在中断
停滞时硬件后备能够复位；后者须单独设计、授权并执行目标板故障注入。

测试结果应报告实际配置、通过/跳过数和限制。设备安全值、急停效果、网络
失联行为及时间预算需要在目标机构与板卡上独立测量。生成测试根密钥为公开
夹具，不能用于生产设备。
