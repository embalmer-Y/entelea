### 工作目录关系与可恢复性

新目录是 linked Git worktree，`.git` 指向旧目录中的对象库。
旧目录不是可以随意删除的独立压缩归档：删除它会破坏新树；
移动其中任一工作目录后需按 Git worktree 文档修复路径，不能手改指针碰运气。
归档操作只移动旧目录，不清理其中 `.deps`、环境、缓存或私有配置。
主仓库与 Forge 的 tracked 状态必须持续保持干净；不在旧树修补代码。

移动不保证旧 `.venv` 的 shebang、CMake cache、SDK 绝对路径仍有效。
重现源码使用固定提交和依赖来源，不复制缓存：
从可访问的旧仓库/现有远端克隆，检出上述基线，再初始化固定 Forge gitlink。
从现有远端取得不了本地未推送基线时，以本地仓库或显式备份为源，
不能把远端旧 main 当成本基线。跨机器仅携带 Git 不会携带忽略的私有文件；
备份这些文件必须另行授权，禁止上传凭据。

## 3. 继承与不继承

### 已确认的跨批次不变量

- Entelea 是框架名；框架层称辅助智能/模拟智能，产品场景才称伴侣。
  设备角色、认知能力、行动权限独立，不能由硬件层级推导权限。
- Zephyr MCU 与原生 Linux ARM64/x86 共享语义和适用代码，
  不统一包装全部 OS，不把整套 Zephyr 服务挪进公共头。
- 有界队列/内存/指令/外发、明确来源/时间/所有权/失败。
  接受请求不等于完成；取消不撤回已发生效果；未知非幂等请求不能自动重试。
- 保护、授权、用户确认内容/权限绑定不可绕过。
  开发配置可提高有界预算并试运行候选，不绕验签、安全和外发边界。
- 云模型不可用时停用智能；独立 App/固定功能按实际依赖继续，
  不伪装离线本地智能。云失败与硬件安全故障不是同一状态机。
- 记忆、情感、图像、音频、显示是可选模块；采集不等于保存/上传/经历。
  媒体只建窄接口与适用后端，不预建完整媒体图。
- 伴侣产品和启用经历记忆的配置要求 >8 GB TF；
  缺卡/不可恢复时保留安全/设置/修复，不自动创建空角色。
  这不是所有框架配置的硬件最低要求。
- 新能力以具体候选通过工程验证、受控试用、用户确认再正式启用。
  工程通过、开发者批准、设备版本回读均不等于产品用户验收。

### 不自动继承

旧代码中的 `ts_*`、`CONFIG_TS_*`、TSAP 和 `tessera_agent` 在兼容决策前保留，
不能为了统一名称破坏二进制、协议、持久格式或 Python 导入。
旧 TF/KV 代码不等于经历记忆；旧启动顺序不等于常驻认知；
旧 needs 不等于动态依赖；旧租约不等于资源仲裁；
旧 activate/rollback 不等于完整试用/晋升。
独立诊断结果、native_sim 桩通过、历史板卡验证不继承为新产品通过。
Forge 为独立工程工具，不内嵌设备大脑，不复制整个工厂进固件。
Galatea/Kaleido 只作固定历史研究参考；本次用户专门授权其整体外移，
不包含提交其现有修改或纳入800项迁移来源。不得再次擅自移动/修改/提交。

## 4. 资产身份、状态与映射规则

清单包含主仓库555项和 Forge245项 Git tree 条目（包含 gitlink）：
repo/固定 commit/tree、原始路径、Git mode/type/object、blob SHA256。
摘要依据 Git 对象字节，不读忽略的私有文件，不按移动后的工作区重新定义基线。
gitlink 用子模块 commit，不编造 SHA256。工作区路径只是本机定位，非资产身份。

- `M-*`：稳定目标模块 ID，`planned_root` 是建议目录。
- `A-*`、`T-*`、`H-*`、`F-*`：机制、测试、诊断、Forge 资产组。
  `N-*` 明确是新实现，无旧来源，不能冒充迁入完成。
- `S-<repo>-<path-hash>`：每个固定源条目的稳定 ID；归档/目标目录改名不改变它。
- 源文件通过 `asset_id -> target_modules -> planned_root` 建立目录对应。
  一对多资产先拆职责，再给每个源项填具体 `target_paths`，
  不能把所有源码复制到全部目标。迁入前该字段为空是**未决**，不是遗漏的既成文件。
- `first_batch` 是首次审查/复用的批次，不承诺整个旧目录在该批次迁完。
  测试/诊断也可能先在 R01 审查，至后续功能批次才适配。

每个源条目选择 `pending_review | migrate | reference | defer | discard`；
`discard` 只是不迁到新树，绝不删除旧基线，须资产 constraints 说明原因。
`migrate` 必须填新文件路径与可解析的本地迁移 commit。
组迁移状态：`not_migrated | in_progress | migrated | blocked | deferred`；
验证状态独立：`not_run | failed | passed`。`migrated` 不等于 `passed`。
新-only 资产用组目标路径/验证证据追踪，没有源项。
源项选择决定完整后才可将组标记 migrated；所有可迁源项均须有提交和目标。

迁入记录至少包含：源条目选择/目标、迁移 commit、合同依据、适用平台、
正/负向验证、未测范围、关键限制和证据路径。
验证 passed 必须有新树可访问的证据文件；迁移工具只校验台账及来源，
**不判断运行时行为或性能通过**。代码移植验收由对应测试完成。
如果同一旧文件要多批拆分：保持源 ID 不变，累计目标路径；组维持 in_progress，
直到全部选择/职责落实，不能先迁部分就宣称整组完成。
已固定 repo/commit/tree 和源条目集合不得日常刷新；引入新历史来源需显式审查、
新增独立 repo ID 与 inventory，不覆盖旧记录。

## 5. 每批统一执行规程

1. 选择一个 ready 批次。所有 `depends_on` 必须 done；
   读取相关资产、旧关键行为、当前窄合同与决策闸。
2. 检查工作树；保留其他智能体修改，冲突先暂停沟通。旧树不修改。
3. 列出精确允许文件、迁移项 disposition/目标、兼容方案和验收命令；
   把相关批次与资产标为 in_progress。需要用户设计确认的项标 blocked。
4. 优先提取确定性机制，再适配平台；按需新增状态机，不打包搬目录。
   每一窄闭环同批迁入必要测试、构建和文档。试验代码默认关。
5. 先小范围正/负向测试，再必要的平台/硬件验证。
   记录 failed/未测与原因，不能删断言、宽泛排除目录、吞错或 mock 生产成功。
6. 更新唯一台账和证据。提交业务/测试后填写其 commit，
   再提交台账更新（避免 commit 自引用）；保持许可和第三方来源。
7. 合同/证据完整且该批次 required gates 全部通过才 done。
   不存在业务代码不能声称固件通过，未测硬件只能 blocked/未验收。

每批预设回退点是“上一批已验证 commit”。失败候选停用、受影响数据保留、
错误可观测；运行时恢复需先安全停输出。工程历史回退只对自己的提交作
非破坏性 revert/补救提交，不 reset --hard、不碰旧归档；
不可逆用户数据迁移在执行前必须定义备份、回滚界限和失败处理。
每批迁移与台账提交允许本地提交；推送、真实硬件、真实云/付费调用另行授权。
