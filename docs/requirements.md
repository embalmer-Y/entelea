## 项目目标和边界

Entelea 是基于 Zephyr 的通用具身 AI 框架：设备能够感知和理解环境、维护
上下文、决策并协调多个 App 读取数据和安全地控制硬件。常驻认知在设备内；
模型推理可位于设备、边缘或云端。设备应同时支持不等待模型的本地快路径
和依赖认知、推理与编排的慢路径。

AI 应能临时生成 Lua 行为以灵活调整硬件控制；复杂、持久的能力由独立的
Forge 工程工厂开发、验证并受控交付。情感能力是设备内可选模块，不需要
情感的设备仍可完成任务。上述方向来自项目需求和现有架构；具体产品形态、
接口和未确定的行为见[待决策事项](#待决策事项)。

Galatea 的产品主线合并到 Entelea：首版实现持续情感、有限自身状态、
可取消任务和受约束主动交互，不另建设备固件。通用任务设备仍可关闭情感，
合法授权任务可作为充分采纳理由，不强制存在陪伴或好奇动机。
原 Galatea 保留为独立研究基线；其门退出、实验和模型不能直接计作设备完成。
职责映射见 [Galatea 产品与研究边界](galatea.md)。

本次合并不启用长期记忆、在线权重学习、做梦巩固、跨设备身份连续或完整
预测脑；这些后续方向需单独确认合同。现有数据、安全、硬件和模型调用
授权边界不变，首版不声称证明现象意识、感质或完整 Galatea 科学能力。

### 交互、数据和执行边界

- 首批情感模块编译时可选，运行时支持启用、禁用和重置；复用单写者内核，
  暂不要求二进制热卸载或多实例。禁用后相同任务仍可执行。
- 首批主动交互默认开启，但必须遵守勿扰、用户说话、冷却、配额和意图时效
  门控；用户可关闭或打断。开启主动交互不等于允许持续上传麦克风或相机
  数据，不把保持安静视为失败。
- 只允许**明确触发的测试语音和单帧图像**外发；设备不保存原始媒体或长期
  记忆。只维护当前任务所需的有界易失上下文，取消或重置后不得重放旧意图。
  SD 验收使用合成测试文件，不以录音、图像或会话历史作为测试文件。
- 真实外发前核对服务端的数据保留政策与授权；设备不落盘不等于服务端不
  留存。日志、测试报告与仓库均不包含原始媒体、会话内容或凭据。
- 能力调用复用 App 权限与安全提交；多 App 通道争用先采用显式申请/释放、
  不隐式抢占，停止或故障后回收。不修改本地/远程来源仲裁；不兼容公开
  合同或安全权限变更仍须审查。
- 回执区分接收、接受、运行、失败、取消和完成；请求/任务标识关联响应，
  取消后的迟到响应不得驱动输出。只有相应可观测证据才能报告物理完成；
  没有观测时只报告可证明的执行状态。

### 验证与指标

- 每模块先做正常、异常、权限、资源、取消及恢复的软件功能验证；允许先
  软件/仿真通过，集中在 H0/I1/I2/I3 做适用真机验证。必需真机场景未通过
  时，需求不得标为“已实现”。
- 本地延迟从输入驱动事件到可观测输出计时；取消从设备接受干预到实际输出
  停止计时。语音首响应从用户说完到喇叭开始有效回答，包含端点检测、
  网络、模型与播放，不能用提示音或收到第一个网络包代替。
- 首批语音产品目标为 **P95 ≤ 1.5 秒**，不是当前性能保证。H0 后、I1 验收
  前冻结测试样本数、负载、端点判定和统计方法；若未达目标，先定位瓶颈并
  确认取舍，不自动放宽阈值。
- 同时测量本地响应/取消延迟、模型超时、CPU、堆/栈/PSRAM、队列/媒体缓冲、
  C5 重连和媒体/SD/网络并发；具体安全值及资源上限在 H0 冻结。无真实
  执行机构或可靠观测的项目声明适用范围，不虚构急停或物理动作验证。

## 进度口径

- **未实现**：尚无满足该项需求的实现；可能存在设计或无关基础组件。
- **部分实现**：已有相关组件或局部链路，但需求、集成或验证尚未完整。
- **已实现**：该行明确限定的范围已经实现，并有与验收条件对应的证据；
  不代表其他配置、物理板卡或整个平台已验证。
- **待确认**：需求是否纳入最终范围或验收方式尚未确定；不能计作已完成。

每行的“需求与验收”给出目标及拟议的可观察结果；带“待定”的接口、范围、
数值和具体方案需要确认后才能最终验收。状态是对该行**全部描述**的判断，
不是按已有代码量估计。若代码存在而目标链路未接通，仍为“部分实现”。
证据指向实现、测试或权威说明；测试目录的存在不等于所有测试已执行或
已经通过。

首次核对参考主仓库 `553149a`、Forge 子模块 `ca5219e` 的代码及本地文档
工作区；后续以文档所在 Git 版本及对应子模块指针为准，未提交修改以
实际工作区为准。以下为定性状态，不给出整体百分比：需求范围、权重、
部分验收指标尚未冻结，任意加权或按行数平均都会误导。每次变更
公开能力时，应在同一变更中更新相关行的状态、缺口和证据；新增或删除
需求应保留稳定编号并记录决定。总进度以本表为准，不维护另一份重复台账。

## 维护与验收

1. 变更需求前核对用户已确认的产品方向；涉及安全、信任或不兼容公开合同
   时遵循[开发与贡献](development.md)的审查要求。
2. 实现后为对应编号补充可复现的测试或检查证据，并记录适用配置、结果及
   局限；状态只有在该行全部验收条件满足时才能改为“已实现”。
3. 硬件安全、物理动作和性能以目标板、实际机构及工作负载的测量为准。
   主机测试、构建成功、模型输出和命令回执不能替代这些证据；板级操作
   需要事先确认设备与风险并获得明确授权。
4. 如果某项需求被取消或拆分，在原编号处注明决定和后续编号，不复用旧
   编号；需求边界、指标或验证方案有变化时同步更新状态。
